## Context

In the [AD3 platform](https://ad3.io/), computational biologists and medicinal chemists routinely inspect 3D protein structures and 2D chemical diagrams. Two specialized libraries handle these tasks:

- **Molstar** — An open-source 3D macromolecular viewer used by the RCSB Protein Data Bank itself
- **RDKit.js** — A WebAssembly port of the industry-standard RDKit cheminformatics toolkit

Both are large (several MB each) and, in the unoptimized AD3 codebase, were bundled eagerly on every route — even pages that never showed 3D or chemical structures. The same Molstar + RDKit combination also ships in [ADC](https://adc.arontier.co/), a related public product built on the same viewer stack.

## Problem

In production, Molstar plus RDKit contributed more than **50% of the main bundle weight** on routes that neither rendered 3D nor displayed molecular diagrams. The standard approach — route-scoped `dynamic()` imports — could solve this cleanly, but required precise knowledge of which routes needed which libraries.

### 2. Route-scoped dynamic imports

Both libraries were migrated from top-level imports to route-scoped `dynamic()` calls:

```tsx
// Before: every route paid the cost
import { MolstarViewer } from '@molstar/viewer'

// After: only routes that render 3D load Molstar
const MolstarViewer = dynamic(() => import('@/components/3d/MolstarViewer'))

// RDKit.js loaded only on compound-related routes
const RdkitDepiction = dynamic(() => import('@/components/chem/RdkitDepiction'))
```

### 3. Loading UX

Each heavy component receives a skeleton placeholder that matches its final dimensions, preventing layout shift (CLS) during lazy load.

Both libraries are genuinely bundled and code-split, not simulated: RDKit.js (~2.5 MB WASM) loads from CDN, and Molstar loads from the `molstar` npm package via `React.lazy()` — the same pattern AD3 itself uses for its viewer component.

## Key decisions

**Why `React.lazy()` for Molstar instead of `next/dynamic`?** `next/dynamic` is built for lazy-loading a single React component; Mol*'s production integration is imperative (`createPluginUI` mounts directly into a DOM container, not through a component tree Next can code-split on its own). Splitting the whole module behind `React.lazy(() => import('./MolstarViewer'))` + `Suspense` defers the entire `molstar` chunk until this component renders — mirroring AD3's own `lazy-molstar.tsx` / `molstar.tsx` split.

**Why `createPluginUI` + `DefaultPluginUISpec` instead of the pre-built Viewer app?** Molstar ships a batteries-included `Viewer.create()` helper (used by molstar.org's own hosted viewer), but production use calls for the lower-level plugin API directly — custom `PluginConfig` to hide every default panel, and a project-specific preset builder for representation styles. `createPluginUI` is what the `Viewer` helper uses internally anyway.

**Does the `molstar` npm package really pull in server-side dependencies?** Its `package.json` lists `express`/`compression`/`cors` — but those belong to a separate part of the package (`model-server`, `volume-server`, bundled CLI tools), never imported by the viewer's UI entry point (`molstar/lib/mol-plugin-ui`). A production build was run against this exact import path to confirm: no server-only module ends up in the client bundle.

**Why CDN for RDKit.js instead of bundling?** RDKit.js is a WebAssembly binary that must be fetched and compiled at runtime regardless of how it's imported. Loading via CDN script tag is the most transparent approach and makes it easy to verify route-scoped loading in DevTools.
