## 배경

[AD3 플랫폼](https://ad3.io/)에서 전산생물학자와 의약화학자들은 3D 단백질 구조와 2D 화학 구조식을 일상적으로 살펴봅니다. 이 작업을 담당하는 전문 라이브러리는 두 가지입니다:

- **Molstar** — RCSB Protein Data Bank 자체에서도 사용하는 오픈소스 3D 거대분자 뷰어
- **RDKit.js** — 업계 표준 RDKit 케모인포매틱스 툴킷의 WebAssembly 포팅 버전

둘 다 용량이 큰데(각각 수 MB), 최적화 이전의 AD3 코드베이스에서는 3D나 화학 구조식을 전혀 보여주지 않는 페이지에서도 모든 라우트에 즉시(eager) 번들링되고 있었습니다. 같은 Molstar + RDKit 조합은 같은 뷰어 스택으로 만들어진 관련 공개 제품인 [ADC](https://adc.arontier.co/)에도 쓰입니다.

## 문제

프로덕션 환경에서 Molstar와 RDKit을 합치면, 3D 렌더링도 분자 구조식도 표시하지 않는 라우트에서조차 **메인 번들 용량의 50% 이상**을 차지했습니다. 표준적인 해법인 라우트 단위 `dynamic()` import로 깔끔하게 해결할 수 있었지만, 그러려면 어떤 라우트가 어떤 라이브러리를 필요로 하는지 정확히 파악하고 있어야 했습니다.

### 2. 라우트 단위 dynamic import

두 라이브러리 모두 최상위 import에서 라우트 단위 `dynamic()` 호출로 마이그레이션했습니다:

```tsx
// 이전: 모든 라우트가 비용을 그대로 부담
import { MolstarViewer } from '@molstar/viewer'

// 이후: 3D를 렌더링하는 라우트만 Molstar를 로드
const MolstarViewer = dynamic(() => import('@/components/3d/MolstarViewer'))

// RDKit.js는 화합물 관련 라우트에서만 로드
const RdkitDepiction = dynamic(() => import('@/components/chem/RdkitDepiction'))
```

### 3. 로딩 UX

각 무거운 컴포넌트는 최종 크기와 일치하는 스켈레톤 플레이스홀더를 받아서, 지연 로드 중 레이아웃 밀림(CLS)을 방지합니다.

## 라이브 데모: 이 사이트에 적용한 같은 기법

아래 패널은 두 라이브러리가 온디맨드로 로드되는 걸 보여줍니다. DevTools → Network를 열고 "rdkit" 또는 "molstar"로 필터링하면 각 라이브러리가 이 페이지에서만 로드되는 걸 확인할 수 있습니다. Molstar 패널에는 작은 preset 전환 버튼(Cartoon / Ball & stick / Surface)도 있는데, 커스텀 `StructureRepresentationPresetProvider` 3개로 구현했습니다 — 실제 플랫폼에서 다른 표현 스타일을 만들 때 쓰는 것과 같은 커스터마이징 메커니즘입니다.

<MolecularViewer />

두 라이브러리 모두 흉내만 낸 게 아니라 실제로 번들링·코드 스플리팅되어 있습니다: RDKit.js(~2.5MB WASM)는 CDN에서 로드되고, Molstar는 `molstar` npm 패키지에서 `React.lazy()`를 통해 로드됩니다 — AD3 자체가 뷰어 컴포넌트에 쓰는 것과 같은 패턴입니다.

## 핵심 판단

**왜 `next/dynamic` 대신 Molstar에 `React.lazy()`를 썼나?** `next/dynamic`은 단일 React 컴포넌트를 지연 로드하기 위한 것인데, Mol*의 프로덕션 통합 방식은 명령형입니다(`createPluginUI`가 DOM 컨테이너에 직접 마운트되지, Next가 알아서 코드 스플리팅할 수 있는 컴포넌트 트리를 통하지 않습니다). 모듈 전체를 `React.lazy(() => import('./MolstarViewer'))` + `Suspense`로 감싸면 이 컴포넌트가 렌더링될 때까지 `molstar` 청크 전체를 지연시킬 수 있습니다 — AD3 자체의 `lazy-molstar.tsx` / `molstar.tsx` 분리 구조를 그대로 반영한 것입니다.

**미리 만들어진 Viewer 앱 대신 왜 `createPluginUI` + `DefaultPluginUISpec`을 썼나?** Molstar는 배터리 포함형 `Viewer.create()` 헬퍼(molstar.org 자체 호스팅 뷰어가 사용)를 제공하지만, 프로덕션에서는 더 저수준의 플러그인 API를 직접 쓰는 게 맞습니다 — 기본 패널을 전부 숨기는 커스텀 `PluginConfig`, 그리고 프로젝트 전용 표현 스타일 preset 빌더가 필요하기 때문입니다. `createPluginUI`는 애초에 `Viewer` 헬퍼가 내부적으로 쓰는 것이기도 합니다.

**`molstar` npm 패키지가 정말 서버 사이드 의존성을 끌고 오나?** `package.json`에 `express`/`compression`/`cors`가 나열돼 있긴 하지만, 이건 패키지의 별도 부분(`model-server`, `volume-server`, 번들된 CLI 도구)에 속하는 것이고, 뷰어의 UI 진입점(`molstar/lib/mol-plugin-ui`)에서는 전혀 import하지 않습니다. 바로 이 import 경로를 대상으로 프로덕션 빌드를 실제로 돌려서 확인했습니다: 서버 전용 모듈은 클라이언트 번들에 전혀 들어가지 않습니다.

**RDKit.js는 왜 번들링 대신 CDN을 썼나?** RDKit.js는 어떻게 import하든 런타임에 fetch·컴파일해야 하는 WebAssembly 바이너리입니다. CDN 스크립트 태그로 로드하는 게 가장 투명한 방식이고, DevTools에서 라우트 단위 로딩을 검증하기도 쉽습니다.
