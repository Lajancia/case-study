## 배경

_이 케이스 스터디는 실제 프로젝트를 기법과 결과 수준으로 재구성한 것입니다. 내부 시스템명·비공개 세부사항은 생략했으며, 측정된 수치는 실제와 동일합니다._

3개의 프론트엔드 제품을 하나의 작은 플랫폼 팀이 담당하고 있었지만, 공용 릴리즈 인프라는 없었습니다 — 제품마다 각자 수동 QA와 필요할 때만 돌리는 보안 점검이 뒤섞인 임기응변식 체계를 각자 키워온 상태였습니다.

## 문제

두 가지 증상이 계속 반복됐습니다:

1. **수동 회귀 테스트가 릴리즈 일정을 갉아먹었습니다.** 영향받은 제품의 UI 전체를 수동으로 한 바퀴 도는 데 릴리즈마다 약 5시간이 걸렸습니다 — 전체 커버리지를 믿고 맡길 수 있는 자동화 파이프라인이 없어서 손으로 직접 했습니다.
2. **보안·품질 점검이 그때그때였습니다.** 의존성/컨테이너 스캔(Snyk), 정적 분석(SonarQube)은 누군가 예전에 한 번 세팅해둔 도구로만 존재했지, 모든 빌드가 거쳐가는 표준 단계는 아니었습니다. 릴리즈 범위 _밖의_ 코드 경로에서 생긴 회귀 — 무관한 변경에 의해 건드려진 공유 컴포넌트 같은 — 가 가끔 발견되지 않은 채 배포됐습니다. "그건 안 건드렸어야 하는데" 싶은 변경사항에 대해 전수 테스트를 다시 돌리는 장치가 없었기 때문입니다.

## 진행한 작업

### 1. 재사용 가능한 Build-Test-Scan-Deploy Jenkinsfile 하나로 설계

제품마다 각자 파이프라인을 따로 관리하게 두는 대신, 세 저장소 중 어디에든 최소한의 프로젝트별 수정만으로 넣을 수 있는 선언형 Jenkinsfile 하나를 설계했습니다:

```groovy
pipeline {
  agent { docker { image 'cypress/included:13.13.0' } }
  options {
    timeout(time: 30, unit: 'MINUTES')
    timestamps()
  }
  stages {
    stage('Install')   { steps { sh 'npm ci' } }
    stage('Lint/Type') { steps { sh 'npm run lint && npm run typecheck' } }
    stage('E2E (Cypress, full suite)') {
      steps { sh 'npx cypress run --config-file cypress.config.ts' }
      post {
        always {
          archiveArtifacts artifacts: 'cypress/screenshots/**, cypress/videos/**', allowEmptyArchive: true
        }
      }
    }
    stage('Security & Quality Scans') {
      parallel {
        stage('Snyk')      { steps { sh 'snyk container test $IMAGE_TAG || true' } }
        stage('SonarQube') { steps { sh 'sonar-scanner' } }
      }
    }
    stage('Report') { steps { junit 'cypress/results/**/*.xml' } }
  }
}
```

**install → lint/typecheck → 전수 Cypress E2E(컨테이너화) → 보안/품질 스캔 → 리포트/아티팩트**라는 4단계 구조가 공통 계약이 됐습니다. 이제 제품별 Jenkinsfile은 환경변수만 다르고, 구조 자체는 동일합니다.

### 2. Cypress E2E 환경 컨테이너화

기존 테스트 스위트는 머신마다 실행 결과가 들쭉날쭉했습니다 — "제 노트북에서는 됩니다"가 실제로 자주 발생하는 실패 유형이었습니다. 고정된 Docker 이미지(`cypress/included`) 안에서 Cypress를 실행하니 환경 차이가 완전히 사라졌습니다: CI와 로컬 개발 환경에서 동일한 브라우저 버전·의존성이 돌고, 어떤 엔지니어든 같은 이미지로 CI 실패를 로컬에서 재현할 수 있습니다.

### 3. 보안·품질 리포팅 자동화

- **Snyk**는 빌드된 컨테이너 이미지의 알려진 취약점을 파이프라인이 돌 때마다 스캔합니다 — 가끔 하는 수동 점검이 아니라.
- **SonarQube**는 매 빌드마다 정해진 품질 프로파일 기준으로 정적 분석을 수행하고, 합의된 임계치를 넘으면 빌드를 실패시킬 수 있는 Quality Gate를 갖고 있습니다.

이 중 어느 것도 진짜 보안 리뷰를 대체하지는 않습니다. 하지만 "누가 스캐너를 돌렸나"를 "스캐너는 매번 돌고, 매번 리포트를 만든다"로 바꾼 것만으로도, 사람이 기억해서 수동으로 해야 했던 점검의 공백을 메웠습니다.

### 4. diff만이 아니라 전수 스위트 실행

가장 가치 있었던 습관 변화는 도구가 아니라, 릴리즈에 명시된 변경 범위에 대응하는 테스트만이 아니라 **전체** E2E 스위트를 정기적으로 돌리는 것이었습니다. 이 방식은 한 번이 아니라 여러 번, 누구도 의도적으로 건드리지 않은 기능의 회귀를 잡아냈습니다: 프론트엔드 공유 컴포넌트나 백엔드 API 응답 형태가 한 기능을 위해 바뀌면서, 거기 의존하던 다른 기능을 조용히 망가뜨린 경우였습니다. 이걸 자동화된 전수 실행으로 릴리즈 전에 잡는 것은, 배포 후 사용자 신고로 알게 되는 것보다 근본적으로 훨씬 저렴한 실패 방식입니다.
