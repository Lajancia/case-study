## 배경

*이 케이스 스터디는 실제 프로젝트를 기법과 결과 수준으로 재구성한 것입니다. 병원명·기관명·내부 시스템명 등 식별 정보는 익명화했으며, 기법과 대응 과정은 실제와 동일합니다.*

PATH는 병리 슬라이드 이미지(WSI, Whole Slide Image)를 업로드 → 타일링 → 분석 엔진 파이프라인에 태워, 그 결과를 병리 전문의가 검토하는 플랫폼입니다. AD3와는 완전히 별개의 제품으로, 저는 이 파이프라인의 프론트엔드 — 특히 뷰어·인터랙션 UI — 를 담당했습니다.

- **OpenSeadragon** 기반 딥줌 뷰어로 기가픽셀급 슬라이드 이미지를 타일 단위로 렌더링
- **Jotai**로 뷰어 상태(줌·팬·오버레이 토글)를 관리하고, **React Hook Form**으로 분석 파라미터·계정 설정 폼을 처리
- **TanStack Query**로 분석 결과(hotspot, ESD/ICI/TME 분석 등) 조회와 캐싱을 관리

이 제품은 국내 대형 의료기관에 **온프레미스**로 납품되는 것을 목표로 개발됐습니다 — 병원 자체 네트워크 안에 설치되어 운영되는 형태입니다.

## 문제

온프레미스 납품을 앞두고, 고객사(의료기관) 보안팀이 자체적으로 OWASP 기반 자동화 침투 테스트 도구로 애플리케이션을 스캔했고, 뒤늦게 취약점 2건을 통보해왔습니다:

1. **로그인 시 비밀번호 평문 전송** — 요청 바디의 비밀번호가 HTTP 평문으로 전송된다는 지적.
2. **로그아웃 후 Bearer 토큰 미만료** — 로그아웃해도 기존 access 토큰으로 재요청하면 그대로 응답이 돌아오는 문제.

두 지적사항은 성격이 서로 달랐습니다. 1번은 온프레미스 환경에서 HTTPS 인증서 발급이 어려워 **내부망 전제로 HTTP 운영이 합의돼 있던 지점**이라, "그게 왜 문제냐"보다는 "그 전제가 여전히 유효한가"를 확인하는 문제였습니다. 2번은 명확한 **실제 버그**였습니다 — 로그아웃이 세션 쿠키만 지울 뿐 토큰 자체를 무효화하지 않아서, 유출된 토큰을 다른 환경에 넣으면 로그인이 유지되는 시나리오를 팀에서 직접 재현했습니다.

## 진행한 작업

### 1. 지적사항 트리아지

팀 차원에서 두 이슈를 코드·재현 테스트로 확인해 근본 원인을 짚었습니다. 비밀번호 평문 이슈는 HTTPS 재스캔으로 플래그가 사라지는지를 먼저 확인해, "HTTP를 쓰라고 한 건 계약 조건이었다"는 근거를 명확히 하는 방향으로 정리했습니다. 토큰 미만료 이슈는 백엔드 sign-out 처리에서 access/refresh 토큰을 서버 측에서 파기하도록 만드는 수정이 필요하다는 결론을 내리고, 제가 대응 작업(이슈 등록·재현 방식 정리)을 맡아 후속 조치로 넘겼습니다.

### 2. OWASP ZAP으로 재검증 루틴 구축

지적사항이 실제로 해소됐는지를 팀 자체적으로 재확인할 방법이 없었기 때문에, **OWASP ZAP**(Zed Attack Proxy)을 설치·설정해서 로그인 플로우를 HTTP/HTTPS 각각 재스캔하는 절차를 만들었습니다. React SPA 특성상 일반적인 Spider로는 페이지를 제대로 크롤링하지 못해 — 로그인이 폼 submit이 아니라 JS `fetch` POST이기 때문에 — AJAX Spider로 전환하고, 브라우저로 직접 로그인시켜 인증 상태를 ZAP에 학습시키는 방식으로 스캔 환경을 구성했습니다.

이 재스캔은 "취약점 0건을 공식 인증받았다"는 의미는 아닙니다 — 고객사가 통보한 특정 지적사항이 재현되는지, 대응 후에도 남아있는지를 저희 쪽에서 자체적으로 확인하기 위한 검증 수단으로 도입한 것입니다. 스캔을 파이프라인에 상시 편입하는 안도 논의했지만, 이번 납품 범위에서는 정례화 단계까지는 가지 못했습니다.

### 3. 뷰어 인터랙션 안정화

납품 준비 과정에서 뷰어 쪽 작업도 병행했습니다 — 줌/팬 상태를 Jotai atom으로 일원화해 여러 오버레이 패널(ROI, hotspot 결과)이 뷰어 좌표계와 어긋나지 않도록 동기화하고, 분석 파라미터 입력 폼의 유효성 검증을 React Hook Form 스키마로 정리했습니다.
