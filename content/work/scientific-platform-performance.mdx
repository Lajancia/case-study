## 배경

이 제품은 단백질-리간드 상호작용을 연구하는 전산생물학자 및 의약화학자가 사용합니다. 연구자들은 3D 분자 뷰어, 구조화학 라이브러리, 인터랙티브 차트 등 무거운 도메인 도구를 브라우저에서 사용하여 가설을 탐색하고 검증합니다.

## 문제

메인 JavaScript 번들이 **32MB**였습니다. Lighthouse Performance 점수는 프로덕션 빌드에서 **29**에 불과했습니다. `rollup-plugin-visualizer` 트리맵 분석 결과, **RDKit과 Molstar가 사용되지 않는 라우트에서도 번들의 50% 이상을 차지**하고 있었습니다 — 사용자가 해당 라우트에서 절대 사용하지 않을 수도 있는 과학 라이브러리의 전체 비용을 모든 페이지가 부담하고 있었습니다.

## 수행한 작업

### 1. 측정

프로덕션 빌드에 `rollup-plugin-visualizer`를 실행하여 가장 심각한 원인을 식별했습니다. 트리맵은 로드 시간 프로파일링이 암시했던 바를 확인해주었습니다: RDKit(구조화학)과 Molstar(3D 분자 뷰어)가 현재 라우트와 관계없이 번들을 지배하고 있었습니다.

### 2. 대안 평가

전역 압축(`brotli`/`gzip`)은 전송 크기를 줄여주지만, 브라우저가 파싱하고 실행해야 하는 32MB 자체는 줄여주지 못합니다 — 압축은 증상만 치료할 뿐 로드 비용 자체를 해결하지 않습니다. 무분별한 `React.lazy` 적용은 비용을 이동시킬 뿐, 관련 없는 라우트에도 과학 라이브러리를 포함시키는 아키텍처 자체는 개선하지 않습니다. 이 코드베이스에는 어느 접근법도 충분하지 않았고, 구조적인 수정이 필요했습니다.

### 3. 라우트 스코프 Molstar/RDKit 청크

Molstar와 RDKit이 실제로 3D 또는 구조화학 뷰를 렌더링하는 라우트에서만 로드되도록 번들링 전략을 재구성했습니다. 테이블 중심, 폼 중심, 대시보드 뷰를 제공하는 라우트는 더 이상 이러한 라이브러리를 메인 청크에 포함하지 않습니다.

### 4. 선택적 RDKit 번들 임포트

RDKit은 C++ 화학정보학 라이브러리의 모놀리식 JavaScript 포트를 제공합니다. 전체 라이브러리 임포트를 대상별 트리-쉐이커블 진입점으로 대체하여, 각 라우트에 필요한 분자 연산만 임포트하도록 했습니다.

### 5. react-plotly.js 지연 로딩

인터랙티브 플로팅 라이브러리가 모든 라우트에 eager 번들링되고 있었습니다. 라우트 레벨 동적 임포트로 지연시켜, 실제로 사용하는 특정 분석 뷰에서만 로드되도록 했습니다.

### 6. Compound Designer — 최적화 경로

Compound Designer 라우트는 **150개 이상의 React 노드**로 구성된 인터랙티브 워크스페이스를 렌더링합니다: 분자 뷰어, 속성 테이블, 필터 패널, 유사성 검색 결과, 평행 좌표 플롯 등. 병목 지점은 다음과 같았습니다:

- **뷰포트 로딩**: 현재 뷰포트에 보이는 노드만 렌더링됩니다. 사용자가 스크롤하거나 패닝하면 나머지 노드가 온디맨드로 활성화됩니다.
- **병렬 렌더링**: 독립적인 노드 트리가 직렬이 아닌 동시에 렌더링됩니다.
- **`useEffect` 의존성 배열 수정**: 여러 효과가 누락되거나 오래된 의존성 배열로 인해 매 렌더링마다 재실행되고 있었습니다. 이를 수정하여 상호작용당 수천 번의 불필요한 리렌더링을 제거했습니다.
- **메모이제이션**: 지문 생성, 유사도 점수, 속성 계산 등 고비용 연산을 안정적인 입력에 키잉된 `useMemo`로 캐싱했습니다.

### 7. CLS 회귀 수정

배포 과정에서 누적 레이아웃 시프트 회귀가 발견되었습니다: 동적 콘텐츠 로딩이 Compound Designer 라우트에서 레이아웃 점프를 유발했습니다. 원인 — 스타일이 없는 로딩 컨테이너가 높이 0으로 축소되는 현상 — 을 식별하고 프로덕션에 도달하기 전에 해결했습니다.

## 동일한 기법, 이 사이트에 적용

이 케이스 스터디 사이트 자체도 동일한 라우트 스코프 코드 스플리팅과 스탠드얼론 빌드 전략을 사용합니다. 이를 입증하기 위해 `perf/before-optimization` 브랜치에서 이 사이트에 AD3의 정확한 안티패턴을 재현했습니다:

- **Eager import:** `three.js` (99 KB)가 `layout.tsx`를 통해 모든 라우트에서 로드됨
- **비스탠드얼론 빌드:** `next.config.ts`에서 `output: 'standalone'` 제거

아래 대시보드는 최적화 전 브랜치와 현재 최적화 상태를 이 사이트에서 직접 비교합니다 — AD3의 클로즈드소스 코드베이스가 아닙니다.

## Docker: 스탠드얼론 빌드 비교

이 프로젝트는 `next.config.ts`에 Next.js `output: 'standalone'`을 사용하여, 애플리케이션 실행에 필요한 런타임 의존성만 포함된 최소 자체 포함 빌드를 생성합니다.

`Dockerfile`은 3단계 빌드를 사용합니다:

```dockerfile
# Stage 1: 의존성 설치
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci

# Stage 2: 빌드
FROM node:22-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . ./
RUN npm run build

# Stage 3: 최소 runner
FROM node:22-alpine AS runner
WORKDIR /app
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public
```

핵심은 `COPY --from=builder /app/.next/standalone ./`입니다. Next.js의 스탠드얼론 출력은 필요한 런타임만 번들링하여 `devDependencies`, 빌드 도구, 캐시 중간물을 제거합니다.

> **참고:** 측정 머신에서 Docker 데몬을 사용할 수 없었습니다. 비스탠드얼론 추정치는 일반적인 Next.js + MDX + Tailwind 프로젝트의 `node_modules` 크기를 기준으로 합니다. 스탠드얼론 수치는 실제 `.next/standalone/` 디렉토리에서 측정했습니다.

## 검증 방법

1. **저장소 클론:** `git clone https://github.com/Lajancia/case-study`
2. **현재 빌드 (최적화):** `git checkout main && npm run build && node scripts/measure-bundle.mjs`
3. **최적화 전 빌드:** `git checkout perf/before-optimization && npm run build && node scripts/measure-before.mjs`
4. **차이 비교:** `git diff perf/before-optimization..main -- app/layout.tsx next.config.ts`
5. **라우트 스코프 청크 확인:** DevTools → Network 탭을 열고 이 페이지로 이동하면 `apexcharts`가 이 라우트에서만 별도 청크로 로드되는 것을 확인할 수 있습니다.
