## Context

*This case study reconstructs real work at the level of technique and outcome. Internal system names and non-public details are omitted; the measured figures are as recorded.*

The product ([AD3](https://ad3.io/), live) serves computational biologists and medicinal chemists investigating protein–ligand interactions. Scientists rely on heavyweight domain tools — 3D molecular viewers, structural chemistry libraries, and interactive charting — to explore and validate hypotheses in the browser. Two specialized libraries handle the visualization work:

- **Molstar** — An open-source 3D macromolecular viewer used by the RCSB Protein Data Bank itself
- **RDKit.js** — A WebAssembly port of the industry-standard RDKit cheminformatics toolkit

Both are large (several MB each), and the same Molstar + RDKit combination also ships in the [ADC case study](/en/work/adc-visualization), a related product built on the same viewer stack.

## Problem

The main JavaScript bundle weighed **32MB**. Lighthouse Performance scored **29** on production builds. A `rollup-plugin-visualizer` treemap revealed that **RDKit and Molstar occupied more than 50% of the bundle on routes where neither was used** — every page paid the full cost of scientific libraries the user might never touch on that route. The standard fix — route-scoped `dynamic()` imports — could solve this cleanly, but required precise knowledge of which routes needed which libraries.

## What I did

### 1. Measure

I ran `rollup-plugin-visualizer` against the production build to identify the worst offenders. The treemap confirmed what load-time profiling suggested: RDKit (structural chemistry) and Molstar (3D molecular viewer) dominated the bundle regardless of the current route.

### 2. Evaluate alternative approaches

Global compression (`brotli` / `gzip`) would reduce transfer size but doesn't change the 32MB that the browser must parse and execute — compression treats the symptom, not the load cost. Indiscriminate lazy loading via `React.lazy` on every heavy import shifts the cost without addressing the architecture that puts scientific libraries on every route regardless of relevance. Neither approach was sufficient for this codebase; the fix needed to be structural.

### 3. Route-scoped Molstar/RDKit chunks

I restructured the bundling strategy so that Molstar and RDKit are loaded only on the routes that actually render 3D or structural chemistry views. Routes that serve table-heavy, form-heavy, or dashboard views no longer include these libraries in their main chunk.

### 4. Selective RDKit bundle imports

RDKit ships a monolithic JavaScript port of its C++ cheminformatics library. I replaced full-library imports with targeted, tree-shakeable entry points — importing only the molecular operations each route needed.

### 5. Lazy react-plotly.js

The interactive plotting library was being eagerly bundled into every route. I deferred it with route-level dynamic imports so that it loads only on the specific analysis views that use it.

### 6. Compound Designer — the critical path

The Compound Designer route renders an interactive workspace with **150+ React nodes**: molecule viewers, property tables, filter panels, similarity search results, and parallel coordinate plots. The bottlenecks were:

- **Viewport loading**: Only nodes visible in the current viewport are rendered. As the user scrolls or pans, remaining nodes hydrate on demand.
- **Parallel rendering**: Independent node trees render concurrently instead of serially.
- **Corrected `useEffect` dependencies**: Several effects were re-running on every render because of missing or stale dependency arrays. Fixing these eliminated thousands of unnecessary re-renders per interaction.
- **Memoization**: Expensive computations — fingerprint generation, similarity scoring, property calculation — are cached with `useMemo` keyed on stable inputs.

### 7. CLS regression

During rollout, a Cumulative Layout Shift regression was detected: dynamic content loading caused layout jumps on the Compound Designer route. The root cause — an unstyled loading container collapsing to zero height — was identified and resolved before the changes reached production.

Both libraries were migrated from top-level imports to route-scoped `dynamic()` calls:

```tsx
// Before: every route paid the cost
import { MolstarViewer } from '@molstar/viewer'

// After: only routes that render 3D load Molstar
const MolstarViewer = dynamic(() => import('@/components/3d/MolstarViewer'))

// RDKit.js loaded only on compound-related routes
const RdkitDepiction = dynamic(() => import('@/components/chem/RdkitDepiction'))
```

Each heavy component receives a skeleton placeholder that matches its final dimensions, preventing layout shift (CLS) during lazy load — the same principle behind the CLS fix in item 7 above.

The panel below demonstrates both libraries loading on-demand. Open DevTools → Network and filter by "rdkit" or "molstar" to see each library load only on this page. The Molstar panel also includes a small preset switcher (Cartoon / Ball & stick / Surface) — three custom `StructureRepresentationPresetProvider`s, the same customization mechanism used to build alternate representation styles on the real platform.

<MolecularViewer />

Both libraries are genuinely bundled and code-split, not simulated: RDKit.js (~2.5 MB WASM) loads from CDN, and Molstar loads from the `molstar` npm package via `React.lazy()` — the same pattern AD3 itself uses for its viewer component.

**Why `React.lazy()` for Molstar instead of `next/dynamic`?** `next/dynamic` is built for lazy-loading a single React component; Mol*'s production integration is imperative (`createPluginUI` mounts directly into a DOM container, not through a component tree Next can code-split on its own). Splitting the whole module behind `React.lazy(() => import('./MolstarViewer'))` + `Suspense` defers the entire `molstar` chunk until this component renders.

**Why CDN for RDKit.js instead of bundling?** RDKit.js is a WebAssembly binary that must be fetched and compiled at runtime regardless of how it's imported. Loading via CDN script tag is the most transparent approach and makes it easy to verify route-scoped loading in DevTools.

1. **Clone this repo:** `git clone https://github.com/Lajancia/case-study`
